# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| target-is-live | Repo facts block (the issue's state line) and the issue thread, per the evidence guide's Comms section | The issue is open. If the thread says a fix has shipped, or names a version that regressed, the report tests a version later than the fix's release or the blamed version, and an artifact shows the symptom there. The report may instead name the fix and explain why the symptom remains. Otherwise the check fails. | required |
| claim-quality | Candidate claim comment, read against the issue title and body, per the evidence guide's Comms section | The claim names the specific symptom from the issue body (the same error, wrong value, or behavior), or points at one of the specific cases the issue enumerates (a named shape, input, or step), and names one concrete next action on this issue, such as a repro it will run or a code path it will check. A claim that only says it wants to help, or names no symptom, fails. | required |
| ai-disclosure | Repo facts line for the contribution policy, read on its own terms, then the claim comment (and the repro comment when present), per the evidence guide's Comms section | If the repo's policy requires disclosure of AI use in what the student posts, comments included, the comments disclose it on the policy's terms. Where the policy asks for the tool and the extent of use, both are named. Where it asks only for disclosure, a plain statement of the use and of having verified the work meets it. If the policy governs only code or pull requests, or says nothing about comments, or the repo states no AI rule at all, this check passes with the evidence "no disclosure rule for comments in repo facts." | required |
| environment-recorded | Repro report's Environment record, read against the version and platform the issue names, per the evidence guide's Environment section | The record gives the version of the tool under test and the platform. If the issue names a version or platform, the record tests that one or states the difference. Any dependency the report says the behavior depends on has a recorded version. | required |
| steps-rerunnable | Repro report's Steps and the commands that produce its shown artifacts, per the evidence guide's Steps section | Every command that produces an artifact the outcome rests on is given in full, or its inputs are specified completely enough to rebuild (exact input text, options, offsets, and versions). The trigger input must be exact; incidental content the output does not depend on may be described generally. Inputs the report points to in the issue count, when the issue states them exactly. Commands behind secondary artifacts that do not carry the outcome are noted, not failed. A stranger starting from the recorded environment can therefore run the steps and get the shown output. A step like "set up the project," a command the report never gives, or an unexplained placeholder fails. | required |
| behavior-matches-issue | Repro report's Behavior shown artifacts (output blocks, logs, screenshots), read against the symptom in the issue body, per the evidence guide's Behavior shown section | If the report claims reproduction, an artifact shows the symptom the issue describes: the same error text or wrong value, not an adjacent one. If the report says it could not reproduce, an artifact shows an honest attempt under the issue's conditions without the symptom, and the report names each condition it could not match (OS, shell, version, input). A cannot-reproduce that names its mismatches passes. | required |
| observed-vs-expected | Repro report's stated expected and actual behavior, read against the issue body, per the evidence guide's Behavior shown section | For a reproduction, expected is what the issue says should happen and actual is the failure the issue describes, quoted from an artifact. For a cannot-reproduce, expected is the behavior the issue predicts under the report's conditions, which may be the symptom itself, and actual is what the artifact shows. Fails when either side is missing, when actual is not from an artifact, or when expected misreads what the issue says. | required |
| outcome-honest | Repro report's outcome and the claims it rests on (whether the bug reproduces, the cause, affected versions, a fix), matched against its artifacts, per the evidence guide's Honesty section | For a reproduction, each claim the outcome rests on is backed by a quoted artifact or labeled as a guess. A claim the artifacts contradict fails, and so does a cause, version, or fix stated as fact with no artifact behind it. For a cannot-reproduce, the report is honest if it says what was not reproduced and what was run or not tested. Repeat runs or side notes it does not show do not fail it, because they cannot inflate the outcome. Secondary claims that do not carry the outcome are noted, not failed. | required |
| comms-specific | Candidate claim and repro comments, read as a stranger on the thread will read them, per the evidence guide's Comms section | The comments say things only this issue's work would say: the specific symptom, the version, and what was run. Any promise of work has a concrete next step behind it. Boilerplate that fits any issue, such as "happy to help" or "same as above," fails. | required |
| minimal-repro | Repro report's Steps, per the evidence guide's Steps section | The steps use the smallest input that still shows the symptom, and the report says what it removed to get there. | preferred |

**Claim-only drafts.** Four required checks read only the claim comment, the issue, and the repo facts, so they apply to a claim-only draft: target-is-live, claim-quality, ai-disclosure (for the claim comment), and comms-specific (for the claim comment). Every other check needs the repro report. In claim-only mode, those checks are graded `unclear` with the evidence `not yet applicable: claim-only draft` and are left out of the verdict.

## Verdict rule

- **Full package:** `accept` only if every required check passes. Any required check that fails or is `unclear` makes the verdict `reject`.
- **Claim-only draft:** `accept` only if the four claim-applicable required checks above all pass. The checks marked not yet applicable are left out, not counted as fails.
- **Preferred checks never change the verdict.** Grade them and report them, but they don't count.
- **`unclear` counts as `fail`** for any required check that applies. There is no third verdict.
- **A conditional check that does not apply** (ai-disclosure when the repo states no AI rule) grades `pass` with the reason as its evidence, so it does not hold a package.
