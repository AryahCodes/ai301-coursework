# Rubric: is this plan ready to post and build from?

## Checks

Evidence names the lists that `procedure.md` builds while reading (Observed runs, Causal claims, Scope items, Approach steps, Tests, Certainty assertions, Thread signals, Comment commitments, Conventions) and the evidence-guide section that says where each list comes from.

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-follows-evidence | Causal claims read against the Observed runs and the differences between passing and failing runs (evidence guide: Diagnosis and grounding) | The stated cause is consistent with every Observed run, and it explains every difference between the passing and failing runs (environment, flags, versions, input position, controls). It fails if a cause contradicts an observed run, or if a difference between runs is dismissed as irrelevant without a run that varies only that factor. A mechanism the plan has not traced is acceptable here; whether it is labeled as untested is judged by honesty-about-unknowns. If the package has no Observed runs, the check fails. | required |
| cause-not-symptom | Causal claims read against the Approach steps (evidence guide: Diagnosis and grounding, Executability) | The planned change alters the mechanism the Causal claims name. A plan whose change only hides, rewords, or special-cases the observed failure, without changing that mechanism, fails. | required |
| reproduction-link | Tests matched against the Observed runs' commands and expected output (evidence guide: Test plan) | At least one test re-runs a command or step from the Observed runs, or the issue's own test case, and names the observable result that shows the fix. A plan whose test is only "run the tests" or "verify the fix" fails. | required |
| bounded-scope | Scope items read against the Causal claims (evidence guide: Scope) | The plan names the files or areas it changes and at least one explicit out-of-scope item, and every named file is needed by a Causal claim. A plan that bundles an unrelated fix, refactor, or docs rewrite fails. | required |
| executable-steps | Approach steps, or where there is no Approach section, the action statements in Scope and Files (evidence guide: Executability) | Each step names a specific file, module, function, or command, and an action, in an order a stranger can follow without asking the author. A named module with a concrete action passes, and exact functions the plan states it will pin down during tracing are an open question, not a failure. A broad area such as "the sync code" or "the rendering layer" does not count as a named module. A plan whose approach is only goals ("make it robust," "clean up the parser") fails. | required |
| test-plan-observable | Tests (evidence guide: Test plan) | Each decisive test names a concrete command or observable step with the expected output or exit status. The tests cover the failing case, and they name a control: the control run the Observed runs used, a named reference behavior, or an existing test that covers the behavior that must not change. A plan with only generic test language fails. | required |
| honesty-about-unknowns | Certainty assertions read against the Causal claims, the Observed runs, the thread signals, and the code locations the plan names (evidence guide: Honesty) | A causal claim is backed if an Observed run, a quoted thread signal, or a code location the plan names supports it. This check fails only if (a) a causal claim contradicts an Observed run, (b) an outcome is asserted as certain with no test in the plan that could show it false, or (c) a named unknown, from the plan or the thread, is presented as resolved. A backed claim needs no hypothesis label. | required |
| comment-matches-plan | Comment commitments read against the plan's Causal claims, Scope items, and next step (evidence guide: Comms) | The plan comment states no cause, scope item, or change that contradicts the plan, and it makes no dated or quantified commitment the plan does not back (a deadline, a count of PRs, "this week"). Conditional or procedural follow-ups ("if X lands I will rebase," "I'll report back") and omissions are not failures. | required |
| thread-aware | Thread signals read against the plan comment (evidence guide: Comms) | Every thread signal that directs the plan or contradicts it is addressed in the plan comment: the plan follows it, or the comment explicitly defers or disputes it with a reason. Supporting remarks need no response. If the thread holds no directing or contradicting signal, the check passes with the evidence "no maintainer direction or contrary observation in thread." | required |
| repo-conventions | Conventions (repo facts and any stated contribution or AI-use rule) read against the plan and the plan comment (evidence guide: Comms) | The plan and the comment meet every stated convention that applies to them, including AI-use disclosure where the stated rule covers comments. If no stated convention applies, the check passes with the evidence "no applicable convention in repo facts." | required |
| blast-radius | Approach steps and Tests (evidence guide: Scope) | The plan names what else the change could affect and how it will check that. | preferred |

## Verdict rule

- **accept** only if every `required` check passes. **reject** if any `required` check fails or is `unclear`. The verdict is binary; there is no third verdict.
- `unclear` counts as `fail` for any `required` check.
- `preferred` checks are graded and reported, and they never change the verdict.
- A check whose pass condition is met by an absence (no thread signals, no applicable convention) passes, with that absence stated as its evidence. It is not `unclear`.
- A package with no Observed runs fails `diagnosis-follows-evidence` and `reproduction-link`, so it is rejected.
